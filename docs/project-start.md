# Старт на проекта – репо и първи задачи

Последна редакция: 2026-11-08

## Какво правиш ти преди първата задача

Тези стъпки са за теб, защото изискват твои акаунти и инсталации на компютъра ти. ИИ не може да ги свърши вместо теб.

- [x] Създай GitHub репо с име `printko3d` и качи в него съдържанието на тази папка. Репото е публично, вижте [решение 0004](decisions/0004-public-repository.md)
- [x] Инсталирай Docker Desktop, текущата LTS версия на .NET SDK и текущата LTS версия на Node.js
- [x] Създай акаунт в render.com. Не въвеждай платежна карта, докато не си проверил какво включва безплатният план
- [x] Включи защита на клона `main`: без директни промени, само през pull request
- [x] Включи в GitHub проверката за изтекли тайни и автоматичните предупреждения за уязвими пакети

Документите, `CLAUDE.md` и структурата на папките вече са в репото.

## Структура на репото

Всичко е в едно репо, с backend, frontend и тестове на ясно разделени места.

```
printko3d/
├─ CLAUDE.md                  правила за код и работа с ИИ
├─ README.md                  как се стартира проектът
├─ docker-compose.yml         API, магазин, админ панел и PostgreSQL локално
├─ render.yaml                настройки на услугите в render.com
├─ .editorconfig
├─ .github/workflows/ci.yml   проверки при всеки pull request
├─ docs/
│  ├─ requirements.md
│  ├─ data-model.md
│  ├─ project-start.md
│  ├─ decisions/              записани решения
│  └─ tasks/                  описания на задачите за ИИ
├─ src/
│  ├─ backend/
│  │  ├─ Storefront.Domain/
│  │  ├─ Storefront.Application/
│  │  ├─ Storefront.Infrastructure/
│  │  ├─ Storefront.Api/
│  │  └─ Dockerfile
│  └─ web/                    npm workspaces за трите frontend пакета
│     ├─ storefront/          публичният магазин (React, TypeScript, Vite)
│     │  ├─ src/features/     catalog, cart
│     │  ├─ src/locales/      bg и по-късно en
│     │  └─ Dockerfile
│     ├─ admin/               админ панел (React, TypeScript, Vite)
│     │  ├─ src/features/     categories, products, images, settings, orders
│     │  ├─ src/locales/
│     │  └─ Dockerfile
│     └─ shared/              общ код: API клиент и типове, UI компоненти, помощни функции
└─ tests/
   ├─ Storefront.UnitTests/
   ├─ Storefront.IntegrationTests/
   └─ e2e/                    Playwright
```

- **Общо име в кода.** Проектите се казват `Storefront`, а не `Printko`. Така кодът не носи името на конкретен магазин и може да се използва за друг. Името „Принтко 3Д“ живее само в настройките на магазина.
- **Едно репо.** За един човек и ИИ е по-лесно промяна, която засяга API и сайта, да е в един pull request и да се тества заедно.
- **Backend по слоеве.** Четирите проекта следват правилата за зависимости от `CLAUDE.md`.
- **Магазин и админ панел са отделни приложения.** Така админ кодът и админ адресът не се зареждат при клиентите и могат да се защитят отделно. Общото, като API клиента и типовете, стои в `shared` и не се дублира.
- **Тестове извън `src`.** Те не влизат в Docker образите за внедряване.

В репото към момента съществуват само папките и файловете, които не зависят от код. Файловете, които липсват (`docker-compose.yml`, `render.yaml`, `ci.yml`, проектите на backend и frontend), се създават със задачите по-долу.

## Задачи по ред

Всяка задача е един pull request, който се прегледа за около 15 минути и оставя проекта в работещо състояние. Следващата започва, когато предишната е слята.

| № | Задача | Какво се получава |
| --- | --- | --- |
| 1 | Скелет и Docker | `docker compose up` стартира API, магазин, админ панел и база. Магазинът и админ панелът показват състоянието на API |
| 2 | CI | Проверки при всеки pull request: build, форматиране, тестове |
| 3 | Модел и миграция | Петте обекта от документа за модела и първа миграция, с интеграционни тестове за ограниченията |
| 4 | Демо данни | Команда, която зарежда 16-те фалшиви продукта |
| 5 | API за четене | Категории, списък на продукти със страниране и филтър, продукт по слъг, настройки на магазина |
| 6 | Основа на сайта | Оформление, тема и имена от настройките, файлове с преводи, лента „демо версия“ |
| 7 | Списък на продуктите | Страница на категория със страниране |
| 8 | Страница на продукт | Галерия, избор на вариант, наличност или срок за изработка |
| 9 | Демо в render.com | Внедряване от `main` с демо данни |
| 10 | Вход за администратор | ASP.NET Identity, роля Admin, двуфакторна защита, всички админ адреси затворени по подразбиране, тестове за достъпа |
| 11 | Админ: категории | Списък, създаване, редакция, подредба и деактивиране |
| 12 | Админ: продукти и варианти | Създаване и редакция, статуси Draft, Published и Archived, проверки като „по поръчка“ изисква срок за изработка |
| 13 | Админ: снимки | Качване, подредба, основна снимка и `alt` текст, с проверка на тип и размер на файла |
| 14 | Админ: настройки на магазина | Име, валута, език, контакти, основен цвят и лента „демо версия“, с версия на реда ([0019](decisions/0019-store-settings-row-version-and-currency-lock.md)). Логото не влиза: качването и показването му са отделна задача след 15 |
| 15 | SEO и достъпност | Заглавия и описания, карта на сайта, проверка по WCAG 2.1 AA |

Този списък покрива каталога и админ панела за него. Количката, поръчките, плащането, доставката и управлението на поръчки от админа идват в следващ списък, след като демото на каталога работи и е прегледано. Индивидуалните поръчки са след тях.

Преди задача 13 трябва да се реши къде стоят качените снимки. Файловата система на render.com се изчиства при ново внедряване, освен ако не е на постоянен диск или във външно хранилище. Затова качването се пише зад интерфейс, а конкретното хранилище се избира отделно. Решено в [0018](decisions/0018-product-images-in-s3-compatible-storage.md): S3-съвместимо хранилище зад `IImageStorage`, засега Supabase Storage.

### Чака: двуфакторна защита на администратора (условие преди продукция)

Задача 10 прави вход само с имейл и парола. Двуфакторната защита (TOTP) е отложена по решение [0013](decisions/0013-defer-two-factor-until-before-production.md), за да не се товари ръчното тестване на демото. Тя е отделна задача и **трябва да е готова, преди в продукция да влязат истински данни и потребители**. Докато не е готова, предпазител в API отказва да стартира със включен вход извън `Development` и `Demo`. Задачата включва: настройване на TOTP при първия вход, кодове за възстановяване и какво се прави при загубено устройство, ограничение на опитите за кода, тестове и махане (или замяна) на предпазителя с проверка, че вторият фактор е включен.

### Чака: Postman за ръчни проверки и тестове на API

Собственикът иска да изпробва адресите на API ръчно в Postman и, по възможност, да има и автоматични тестове там. Темата е отделна от задача 10 и ще се разгледа допълнително; нищо от нея не е решено. Какво трябва да се реши, когато дойде редът:

- Какво влиза в репото: колекция (и среда с променливи като адреса на API), или само работното пространство. Към момента Postman разширението е създало в корена на репото `.postman/` и `postman/` (работно пространство, сочещо към `src/web/shared/openapi.json`); те не са commit-нати.
- Откъде идва колекцията: от OpenAPI документа (`openapi.json` е единственият източник на договора, решение 0010) или на ръка. Ръчно писана колекция се разминава с API.
- Как се ползват затворените адреси: вход през `POST /api/v1/auth/login` (бисквитката `__Host-printko-admin` е `Secure`, затова иска `https` или Postman, който я приема) и заглавие `X-Requested-With` за заявките, които променят данни (решение 0014).
- Дали тестовете в Postman са само за ръчна работа, или се пускат и в CI (Postman CLI / Newman). Втората възможност е нов инструмент в CI и иска одобрение. Автоматичните тестове на API вече са интеграционните тестове с `WebApplicationFactory`, така че Postman не ги заменя.
- Тайни: администраторската парола не влиза в колекцията, средата или репото, а се въвежда локално.

### Чака: демо снимки

Страницата на продукта (задача 8) вече показва снимки, но в демото се вижда само вградената снимка по подразбиране. Демо данните имат ключове като `demo/<категория>/<слъг>-<n>.jpg`, а файлове зад тях няма. Не е решено кога се прави; започва се, когато се стигне до него (най-късно преди демото в render.com, задача 9).

Какво трябва да се реши и направи:

- Къде стоят демо файловете и кой ги сервира. Решено в 0018: същият S3-съвместим bucket, публичен за четене; адресът на снимка е `imageBaseUrl` от `config.json` плюс `storageKey` (решение 0011). Остава да се решат ключовете на демо файловете и как се качват (през админ панела или със скрипт).
- Самите файлове: 3 снимки на продукт за 16-те демо продукта (две от тях са към първите два варианта, виж `DemoDataSeeder`). Ползват се само снимки без авторски права и без лични данни.
- Задаване на `imageBaseUrl` в `config.json` и `img-src` в CSP: направено в част 13b на задача 13 (`IMAGE_BASE_URL` в Docker и в `render.yaml`).
- Проверка в браузъра: голяма снимка, миниатюри, снимки по вариант, счупена снимка.
