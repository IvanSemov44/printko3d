## Задача
Добави GitHub Actions workflow, който при всеки pull request към `main` пуска build, проверка на форматирането, linter, тестове на backend и frontend, build на Docker образите, проверка за уязвими зависимости и за изтекли тайни.

## Контекст
- Правилата за CI са в раздела „Docker, среди и CI“ и в раздела „Сигурност“ на CLAUDE.md.
- Командите, които вече минават локално, са в `README.md`: `dotnet build`, `dotnet test`, `dotnet format --verify-no-changes`, `npm run lint`, `npm run format:check`, `npm test`, `npm run build`.
- Dockerfile-овете са `src/backend/Dockerfile` (контекст: корена на репото) и `src/web/docker/Dockerfile` (контекст: `src/web`, аргумент `APP`).
- Интеграционните тестове стартират PostgreSQL с Testcontainers и изискват Docker на машината.
- `npm audit` вече показва 11 умерени находки, всички в `minimatch` през `typescript-eslint` (само за разработка).
- Файлът е `.github/workflows/ci.yml`.

## Критерии за приемане
- Workflow-ът се пуска при pull request към `main` и при push в `main`.
- Backend job: restore, build (предупрежденията са грешки), `dotnet format --verify-no-changes`, `dotnet test` (включително интеграционните).
- Frontend job: `npm ci`, lint, `format:check`, тестове, build.
- Docker job: build на образите за API, магазин и админ панел, без публикуване.
- Проверка за уязвими зависимости: NuGet и npm. Правилото за прага на сериозност се уточнява в плана.
- Проверка за изтекли тайни по цялата история на pull request-а.
- Версиите на Node.js и .NET се вземат от `.nvmrc` и `global.json`, не се повтарят във workflow-а.
- Кешът на NuGet и npm е включен.
- Ако job пропадне, pull request-ът се вижда като неуспешен. Показано е на конкретен пример (временно счупен тест в отделен клон, който не се слива).
- README има кратък раздел за CI и как се пускат същите проверки локално.

## Граници
- Без `render.yaml`, без внедряване и без публикуване на образи.
- Без промени в кода на приложението, освен ако проверка не открие реален проблем. Тогава се спира и се пита.
- Нови пакети: не. Нови GitHub Actions: само след одобрение; в плана се посочва всяка с автор, поддръжка и лиценз. Закачат се към commit SHA, не към таг.
- Не се пипат `docs/` (освен този файл при нужда), `CLAUDE.md` и настройките на защитата на `main`. Тя се настройва от човека в GitHub.
- Тайните не се записват във workflow-а. Ползват се само вградените права на `GITHUB_TOKEN`, с минимални `permissions`.

## Как се проверява
- Pull request от клона на задачата: всички jobs са зелени.
- Втори, неслят клон със счупен тест и счупено форматиране: CI е червен и показва кой job е пропаднал.
- Същите команди локално, както са описани в README.

## Преди да пишеш код
Дай кратък план и списък с предположенията си. Попитай за:
- кои GitHub Actions и инструменти за тайни и уязвимости предлагаш и защо;
- от каква сериозност нагоре уязвимостите блокират pull request-а и как се третират известните находки в dev инструментите;
- кои jobs да са задължителни в защитата на `main` (това го настройва човекът).
