# 14. Сесията на администратора е бисквитка, а панелът препраща заявките към API

Дата: 2026-11-09
Статус: прието (задача 10: бекендът е в 10a, проксито и панелът са в 10b)

## Контекст
Админ панелът и API са отделни приложения на различни адреси. В демото в render.com те са `https://printko3d-*.onrender.com`, а `onrender.com` е в списъка на публичните суфикси, така че браузърът ги смята за различни „сайтове“. Бисквитка между тях иска `SameSite=None; Secure`, а браузърите блокират такива бисквитки на трети страни. `CLAUDE.md` изисква бисквитки `HttpOnly`, `Secure` и `SameSite`.

Разгледани са три пътя: (а) прокси в контейнера на панела, (б) токени за достъп вместо бисквитка, (в) собствен домейн с общ родителски адрес.

## Решение
- Сесията е бисквитка на ASP.NET Identity с име `__Host-printko-admin`: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, без `Domain`, срок 8 часа с плъзгащо подновяване.
- Браузърът говори само с адреса на панела. Nginx на панела препраща `/api/` към адреса от променливата `API_UPSTREAM` (само за панела; в Docker `http://api:8080`, в render.com публичният адрес на API), така че бисквитката е от същия сайт. CORS на API остава само за `GET` и без бисквитки, а не се отваря за запис.
- Защита срещу CSRF: всяка заявка, която променя данни (`POST`, `PUT`, `PATCH`, `DELETE`), трябва да има заглавие `X-Requested-With`, иначе API връща `403`. Браузърът не праща такова заглавие от чужд сайт без CORS проверка, която API не позволява. Това е в допълнение на `SameSite=Strict`.
- Изходът прекратява сесията на сървъра: сменя се security stamp на потребителя и всяко копие на бисквитката спира да работи. Stamp-ът се проверява при всяка заявка. Цената е една заявка към базата за заявка на администратор, а изходът прекратява и сесиите на другите устройства на същия администратор.
- Вариант (б) е отхвърлен: токен в паметта на страницата е по-рисков при XSS и е против правилото за бисквитки. Вариант (в) се връща към разглеждане, когато има собствен домейн.

## Последствия
- CSP на панела не се променя: заявките за вход са към собствения адрес (`'self'`), а проверката на състоянието на API остава към `API_URL`. Заявките минават през един адрес, затова панелът ползва относителни адреси (`/api/v1/auth/...`), а не `apiUrl`.
- Nginx разрешава адреса на API при старт. Ако името не се намира, контейнерът на панела не стартира, докато API не е достъпно по име (в Docker `depends_on` го осигурява).
- `npm run dev` препраща `/api` към API с настройка на Vite (`API_PROXY_TARGET`, по подразбиране `http://localhost:8080`).
- Зад проксито и балансьора на render.com API вижда един и същ IP адрес за всички клиенти, така че ограничението на опитите за вход (по IP) е общо за всички. Заглавията `X-Forwarded-For` още не се ползват, защото доверието към тях е отделно решение (иначе клиентът може да ги подправи). За демо с един администратор това е приемливо. Заключването на акаунта (5 грешни опита, 15 минути) работи независимо от IP.
- Заключването е по акаунт, така че чужд човек може да заключи истинския администратор с грешни пароли. Приема се за демото; ограничението по IP го смекчава.
- Новите адреси са `POST /api/v1/auth/login`, `POST /api/v1/auth/logout` и `GET /api/v1/auth/me`.
