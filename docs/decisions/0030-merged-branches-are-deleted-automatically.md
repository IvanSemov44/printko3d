# 30. Слетите клонове се трият автоматично

Дата: 2026-11-13
Статус: прието

## Контекст

Pull request-ите се сливат със squash (`feat(cart): … (#77)`): в `main` влиза един нов commit, а commit-ите на клона остават с други хешове. След сливане клонът изглежда неслят за `git branch -d`, а слетите клонове на GitHub оставаха и се трупаха (`feat/cart-page`, `feat/cart-rules`, `feat/cart-rest-codes`). Следващата работа се правеше върху клон, започнат от слят клон, и носеше стари commit-и, които трябваше да се ребазират върху `main`.

## Решение

- В настройките на репото на GitHub е включено „Automatically delete head branches“ (`delete_branch_on_merge`, включено на 2026-11-13). Клонът на слят pull request се трие от GitHub.
- Нова задача започва от актуалния `main` (`git checkout main && git pull`), в нов клон по имената от `CLAUDE.md`, никога от слят клон.
- Локалните клонове на слети pull request-и се трият с `git branch -D`, но само след проверка, че pull request-ът е слят и че нито един commit на клона не е само локален (`git log <клон> --not --remotes` е празно).
- Клон, който още няма pull request, не се трие и не се презаписва с форсиран push освен ако е създаден от същия човек минути преди това и няма pull request; тогава е позволен `--force-with-lease`, не `--force`.

## Последствия

- Настройката е в GitHub, не в репото; ако репото се премести или се създаде наново, трябва да се включи пак (пази се тук като запис).
- Следващ клон не носи стари commit-и, така че ребазирането `git rebase --onto origin/main <стария връх>` вече не е нужно.
- Слят pull request може да се възстанови от GitHub (бутон „Restore branch“), докато е видим.
