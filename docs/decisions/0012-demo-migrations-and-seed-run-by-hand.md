# 12. В демото миграциите и демо данните се пускат ръчно, с команди на API

Дата: 2026-11-08
Статус: прието

## Контекст
CLAUDE.md: миграциите са отделна стъпка при внедряване, не автоматично при всеки старт на няколко копия на приложението. Образът на API е само runtime, без .NET SDK, затова `dotnet ef` не може да се пусне в него. Командата `pre-deploy` в render.com според документацията е за платени услуги, а демото е на безплатния план.

Разгледани са три пътя: ръчно от компютъра на разработчика, автоматично при старт на API и платен план с `preDeployCommand`. Вторият нарушава правилото в CLAUDE.md, а третият струва пари.

## Решение
- API получава команда `migrate` (по модела на `seed`). Тя прилага чакащите миграции и излиза. Повторното пускане е безопасно, а сама при старт на API не се пуска.
- Връзката към базата може да се подаде и като адрес `Database__Url` (`postgres://потребител:парола@хост:порт/база`), във вида, в който render.com го дава. API го превежда към Npgsql и никога не го повтаря в съобщение за грешка.
- В демото `migrate` и `seed` се пускат ръчно от компютъра на разработчика срещу външния адрес на базата, при първо внедряване и след всяка нова миграция. Редът е описан в `README.md`.
- Автоматичното внедряване от `main` е със `autoDeployTrigger: checksPass`, а миграциите остават отделна стъпка.

## Последствия
- Нова версия с нова миграция изисква ръчно пускане на `migrate`, иначе API и схемата се разминават. `seed` отказва при неактуална схема, но `/health` проверява само дали базата е достъпна.
- Безплатната база изтича след 30 дни. Демото се възстановява с нова база и пускане на `migrate` и `seed`.
- За продукция това решение не важи: там стъпката за миграции ще се избира отделно, заедно с хостинга.
