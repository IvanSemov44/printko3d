# Принтко 3Д

Онлайн магазин за 3D принтове. Кодът е общ, а всичко, което е специфично за конкретен магазин (име, валута, цветове, контакти), е настройка в базата, така че проектът да може да се ползва и за друг магазин.

## Как се стартира

Нужни са Docker Desktop, .NET SDK (версията е в `global.json`) и Node.js (версията е в `.nvmrc`).

```bash
cp .env.example .env
docker compose up --build
```

| Услуга              | Адрес                        |
| ------------------- | ---------------------------- |
| Магазин             | http://localhost:5173        |
| Админ панел         | http://localhost:5174        |
| API (`GET /health`) | http://localhost:8080/health |
| PostgreSQL          | `localhost:5433`             |
| Писма (Mailpit)     | http://localhost:8025        |

Магазинът и админ панелът показват дали API е достъпно. Портовете се сменят в `.env` (`API_PORT`, `STOREFRONT_PORT`, `ADMIN_PORT`, `POSTGRES_PORT`). Ако порт е зает от друга програма, например друг Vite сървър, `localhost` в браузъра може да отвори нея вместо контейнера. Тогава я спри или смени порта.

## Снимки на продукти

Качените снимки се пазят в S3-съвместимо хранилище (решение [0018](docs/decisions/0018-product-images-in-s3-compatible-storage.md)), не в контейнера. Без настройки всичко работи, само качването на снимка връща грешка. За да го включиш, попълни в `.env` променливите `IMAGE_STORAGE_*` (адрес, регион, име на bucket и двата ключа) и `IMAGE_BASE_URL` (публичният адрес, от който се четат снимките, например `https://<project-ref>.supabase.co/storage/v1/object/public/<bucket>`), после `docker compose up --build`. Ключовете са тайни: само в твоя `.env`, никога в репото.

## Имейл

Магазинът праща писма през интерфейса `IEmailSender` (решение [0031](docs/decisions/0031-email-behind-iemailsender-with-mailkit.md)). С `docker compose up` те отиват в локалния прихващач Mailpit, който не праща нищо навън. Прочиташ ги на http://localhost:8025 (портът се сменя с `MAILPIT_UI_PORT`).

Истински доставчик се включва с `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_USER`, `EMAIL_PASSWORD`, `EMAIL_FROM` и `EMAIL_USE_TLS` в твоя `.env`; паролата е тайна. Празен `EMAIL_HOST` изключва изпращането: писмото се пропуска с предупреждение в журнала (само идентификатор, без адрес и текст), а поръчката не пропада. В демото в render.com `Email__*` са празни, докато не се въведат в таблото; тогава писмата тръгват без промяна на кода.

## Демо данни

Командата `seed` зарежда 16 фалшиви продукта в четири категории и един ред настройки на магазина (`is_demo = true`). Данните са едни и същи при всяко зареждане. Командата работи само в среда `Development` и `Demo`, иначе излиза с грешка. Тя **не прилага миграции** и не се пуска сама при старт на API. Ако схемата липсва, спира и казва какво да направиш.

1. Приложи миграциите върху базата (от хоста; PostgreSQL от `docker compose up db` слуша на порт 5433, вземи паролата от `.env`):

   ```bash
   dotnet tool restore
   export Database__ConnectionString="Host=localhost;Port=5433;Database=storefront;Username=storefront;Password=<паролата от .env>"
   dotnet ef database update --project src/backend/Storefront.Infrastructure
   ```

2. Зареди данните, или локално:

   ```bash
   dotnet run --project src/backend/Storefront.Api -- seed
   ```

   или в Docker (услугата `api` е със среда `Development` по подразбиране; за демо средата задай `ASPNETCORE_ENVIRONMENT=Demo`):

   ```bash
   docker compose run --rm api seed
   ```

`dotnet run` ползва профила от `launchSettings.json`, който задава `Development`. За друга среда добави `--no-launch-profile`, например `ASPNETCORE_ENVIRONMENT=Production dotnet run --no-launch-profile --project src/backend/Storefront.Api -- seed` отказва с код 1.

Повторното пускане е безопасно: продуктите и категориите, които вече ги има (по слъг), се пропускат, а настройките не се презаписват. За начисто изтрий базата (`docker compose down -v`), приложи миграциите и пусни `seed` отново.

## Администратор

Входът в админ панела е с имейл и парола (роля `Admin`, ASP.NET Identity). Двуфакторна защита още няма (решение [0013](docs/decisions/0013-defer-two-factor-until-before-production.md)), затова **API отказва да стартира във всяка среда освен `Development` и `Demo`**, освен ако `AdminLogin__Enabled=false`. Регистрация няма: администраторът се създава с команда, подобна на `seed`. Тя изисква приложени миграции, не печата имейла и паролата и е безопасна при повторно пускане (съществуващ акаунт не се променя).

```bash
# имейл и парола от променливи на средата (паролата е най-малко 12 символа; няма парола по подразбиране)
export Admin__Email="<имейл>"
export Admin__Password="<парола>"
dotnet run --project src/backend/Storefront.Api -- create-admin
```

Ако `Admin__Password` липсва и командата е пусната в терминал, паролата се пита без ехо. Със `docker compose` подай променливите с `-e`: `docker compose run --rm -e Admin__Email -e Admin__Password api create-admin`.

Всички адреси на API са затворени по подразбиране (трябва вход с роля `Admin`). Отворени са само каталогът, настройките на магазина, `/health` и самият вход. Новите адреси са `POST /api/v1/auth/login`, `POST /api/v1/auth/logout` и `GET /api/v1/auth/me`. Заявките, които променят данни, трябва да имат заглавие `X-Requested-With`. В панела влизаш с този имейл и парола (`http://localhost:5174` в Docker, или `npm run dev` в `src/web` с API на порт 8080; `API_PROXY_TARGET` сменя адреса на API за `npm run dev`). Бисквитката е `Secure`, затова локално работи само на `localhost` (Chrome и Firefox го приемат; Safari не). Входът е ограничен до 5 заявки в минута от един адрес (`AdminLogin__LoginAttemptsPerMinute`), а след 5 грешни пароли акаунтът се заключва за 15 минути. Сесията и защитата срещу CSRF са в [0014](docs/decisions/0014-admin-session-cookie-through-panel-proxy.md), ключовете в базата са в [0015](docs/decisions/0015-data-protection-keys-in-database.md).

## API за категориите в админ панела

Под `/api/v1/admin/categories`, само за роля `Admin`: списък с неактивните (без страниране), `GET`/`POST`, `PUT /{id}`, `POST /{id}/activate`, `/deactivate` и `/move` (`direction`: `Up` или `Down`). Категории не се изтриват, само се деактивират. Всеки отговор носи `version`, а редакцията я връща обратно; ако друг е записал междувременно, API връща `409` с код `category.version_conflict`, а за зает слъг `409` с код `category.slug_taken`. Подробности са в [0016](docs/decisions/0016-admin-categories-list-and-row-version.md). Магазинът кешира списъка на категориите до 5 минути, затова промяна се вижда там с такова забавяне.

В панела след вход се отваря `/categories`: дърво с категориите (неактивните са с надпис „Неактивна“), бутони „нагоре“ и „надолу“ за подредба, деактивиране с потвърждение и екрани за създаване (`/categories/new`) и редакция (`/categories/:id`). Слъгът се предлага от името (българска транслитерация) и се сменя ръчно. Деактивирането е само от списъка, а при разминаване на версията формата показва бутон „Презареди категорията“.

## API за четене на каталога

Всички адреси са публични `GET` под `/api/v1`. Показват се само `Published` продукти от активни категории и само активните им варианти. Цените са цели числа в най-малката парична единица, а валутата е в `/store-settings`. OpenAPI документът е на `/openapi/v1.json` (само в среда `Development`).

| Адрес              | Какво връща                                                                                                                                                                                                                                                                                   |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/categories`      | Активните категории, подредени по `sortOrder`                                                                                                                                                                                                                                                 |
| `/products`        | Страница с продукти. Параметри: `category` (слъг, обхваща и подкатегориите; непознат слъг дава празна страница), `fulfilmentType` (`InStock` или `MadeToOrder`), `sort` (`name`, `-name`, `price`, `-price`; по подразбиране `name`), `page` (1–10000), `pageSize` (1–48, по подразбиране 12) |
| `/products/{slug}` | Един продукт с описание, варианти и всички снимки; `404`, ако не се вижда в магазина                                                                                                                                                                                                          |
| `/store-settings`  | Настройките на магазина                                                                                                                                                                                                                                                                       |

Списъците връщат `{ items, page, pageSize, totalCount, totalPages }`. Невалидни параметри дават `400`, липсващ ресурс `404`, и двата във формат `ProblemDetails` с допълнително поле `code` (`validation.failed`, `product.not_found`, `store_settings.not_found`), по което клиентът избира текста. `/categories` е без страниране (решение 0009). Снимките са само с `storageKey`, не с пълен адрес.

## CI

При всеки pull request към `main` (и при push в `main`) GitHub Actions пуска `.github/workflows/ci.yml` с пет jobs: `backend`, `frontend`, `docker`, `audit` и `secrets`. Версиите на .NET и Node.js се вземат от `global.json` и `.nvmrc`.

Същите проверки локално (backend и frontend командите са в раздела по-горе):

```bash
docker build -f src/backend/Dockerfile .
docker build -f src/web/docker/Dockerfile --build-arg APP=storefront src/web
docker build -f src/web/docker/Dockerfile --build-arg APP=admin src/web
dotnet list Storefront.slnx package --vulnerable --include-transitive
(cd src/web && npm audit --omit=dev --audit-level=high)
gitleaks git --redact --verbose
```

`audit` блокира при High и Critical. Находките в dev инструментите (умерени, през `typescript-eslint`) само се показват.

## Демо в render.com

Демото е с фалшиви данни, без реални плащания, на безплатния план. Услугите (база, API, магазин, админ панел) са описани в [`render.yaml`](render.yaml). Внедряването е от клона `main`, когато проверките на GitHub са зелени. Решението за ръчните стъпки по-долу е [0012](docs/decisions/0012-demo-migrations-and-seed-run-by-hand.md).

**Първо внедряване**

1. В render.com: New → Blueprint, избери репото и клона `main`. Render създава `printko3d-db`, `printko3d-api`, `printko3d-storefront` и `printko3d-admin`.
2. Render пита за седем стойности, които не могат да са в репото, защото адресът на една услуга не е известен на друга. Попълни ги с публичните адреси на услугите (виж ги в таблото; ако имената са свободни, са от вида `https://printko3d-api.onrender.com`):
   - `API_URL` на магазина и на админ панела: адресът на API;
   - `API_UPSTREAM` на админ панела: същият адрес на API. Nginx на панела препраща `/api/` към него, така че браузърът говори само с панела и бисквитката на сесията е от един сайт (решение [0014](docs/decisions/0014-admin-session-cookie-through-panel-proxy.md));
   - `Cors__AllowedOrigins__0` на API: адресът на магазина;
   - `Cors__AllowedOrigins__1` на API: адресът на админ панела;
   - `SITE_URL` на магазина и `Site__Url` на API: адресът на магазина (за `canonical`, Open Graph и `sitemap.xml`, решение [0020](docs/decisions/0020-sitemap-from-api-and-soft-404.md)). Демото не се индексира: `ALLOW_INDEXING` не се задава, затова `robots.txt` забранява всичко. Само в продукция `ALLOW_INDEXING=true`.

   За снимките на продукти попълни още (решение [0018](docs/decisions/0018-product-images-in-s3-compatible-storage.md)): `IMAGE_BASE_URL` на магазина и на админ панела (публичният адрес на bucket-а) и `ImageStorage__Endpoint`, `ImageStorage__Region`, `ImageStorage__Bucket`, `ImageStorage__AccessKey`, `ImageStorage__SecretKey` на API. Двата ключа са тайни. Без тях демото работи, само качването на снимка връща грешка.

   Ако имената са заети и render.com добави наставка, или грешиш адрес, поправи стойностите в Environment на услугата. Промяната на `API_URL` изисква ново внедряване.

3. Приложи миграциите и зареди демо данните от компютъра си (нужни са .NET SDK и външният адрес на базата: `printko3d-db` → Connections → External Database URL). Адресът съдържа паролата, затова не го записвай в репото и не го пращай никъде.

   ```bash
   export Database__Url="<External Database URL>"
   dotnet run --no-launch-profile --project src/backend/Storefront.Api -- migrate
   ASPNETCORE_ENVIRONMENT=Demo dotnet run --no-launch-profile --project src/backend/Storefront.Api -- seed
   ```

   Двете команди са безопасни при повторно пускане. `migrate` се пуска и след всяка нова миграция, защото API не я прилага сам.

   След това създай администратора. Паролата не се записва в репото, в `render.yaml` и в логовете: най-безопасно е да я въведеш в терминала, когато командата я поиска.

   ```bash
   export Admin__Email="<имейл>"
   ASPNETCORE_ENVIRONMENT=Demo dotnet run --no-launch-profile --project src/backend/Storefront.Api -- create-admin
   ```

   Командата иска паролата в терминала (или я вземи от `Admin__Password`).

4. Отвори адреса на магазина: началната страница, категория и продукт, цени в евро и лента „демо версия“.

**Какво да знаеш за безплатния план** (по документацията на render.com към 2026-11-08; провери я пак преди да разчиташ на нея)

- Услугите заспиват след 15 минути без заявки, а първата заявка след това отнема около минута. Работните часове са 750 на месец за целия акаунт.
- Безплатната база изтича след 30 дни (има още 14 дни гратисен период) и е до 1 GB. За ново демо създай нова база и пусни `migrate` и `seed`.
- Базата е достъпна и отвън с паролата си. Данните са фалшиви, но ако искаш, ограничи достъпа до своя адрес с `ipAllowList` на базата.
- Безплатният план няма стъпка преди внедряване (`preDeployCommand`), затова миграциите са ръчни.

**Първоначалната проверка след внедряване** е ръчна, от човек: дълбоките адреси (`/categories/<слъг>`, `/products/<слъг>`) се презареждат без грешка, а конзолата на браузъра е без грешки за CORS и CSP. Колко точно трае първата заявка след заспиване, запиши тук след първата проверка: _още не е измерено_.

## Състояние

Към 2026-11-14 са готови задачи 1 до 26 от [`docs/project-start.md`](docs/project-start.md): каталогът и демото в render.com (1–9), вход и админ панел за категории, продукти, снимки и настройки (10–14), SEO и достъпност на магазина (15), наръчникът за инженерната работа (16), дизайн основата (17) и количката (18–21: сървърна количка с анонимна бисквитка, бутон на страницата на продукта, брояч в хедъра, панел и страница `/cart`, лимит спрямо наличността, „по поръчка“ със срок, неактивни и архивирани редове и лента при смяна на цена или наличност). Имейл основа (22: `IEmailSender`, MailKit и локален прихващач Mailpit) и поръчка като гост (23: количката става поръчка с копие на името, SKU и цената, случаен номер `PR-` и осем цифри, форма `/checkout` с преглед и съгласие с Общите условия и страница на приетата поръчка `/order/:номер`). Резервация на наличност (24: поръчката намалява наличността на артикулите „на склад“ в същата транзакция и две едновременни поръчки за последната бройка не минават и двете; връщането при отказ е готов метод, който чака задачи 26 и 28). Доставка (25: тестов куриер зад `IShippingProvider`, цена по тегло от тарифа в базата, избор и цена на доставката на `/checkout` преди потвърждение, доставката е копие в поръчката и част от общата сума, екран „Доставка“ в админ панела за стъпките на тарифата; тарифата за демото се зарежда от `seed`). Плащане (26: тестов доставчик зад `IPaymentProvider`, без картови данни; бутон „Плати“ на `/order/:номер` води към страница „Тестово плащане“ с два бутона, а резултатът минава през подписано съобщение до адреса на доставчика, като при истинско плащане; повторно съобщение не плаща втори път; неплатена поръчка се отказва след 60 минути плюс 5 минути пауза и връща наличността; късно плащане оживява поръчката, ако наличността още е свободна; лента „Тестово плащане и доставка“ на всяка страница, докато доставчикът е тестов; решение [0035](docs/decisions/0035-payment-behind-a-provider-with-signed-messages.md)). Имейл за поръчка и екран за поръчки в админ панела още няма: поръчките са само в базата. Следват статуси и имейли, админ за поръчки и клиентски акаунти (задачи 27 и нататък, виж „Следващ списък“ там).

### Демото в render.com работи

Първото внедряване е направено на 2026-11-08, от `main` чрез [`render.yaml`](render.yaml) (pull request #18):

| Услуга          | Адрес                                     |
| --------------- | ----------------------------------------- |
| Магазин         | https://printko3d-storefront.onrender.com |
| Админ панел     | https://printko3d-admin.onrender.com      |
| API (`/health`) | https://printko3d-api.onrender.com/health |

Какво е проверено на живо: `/health` е здрав и базата е достъпна; `migrate` приложи първата миграция, а `seed` зареди 4 категории, 16 продукта и настройките на магазина (`is_demo = true`); API връща категории, продукт и настройки; `config.json` на магазина и админ панела сочи към API; CORS отговаря за адреса на магазина; дълбок адрес като `/products/dragon-3d-puzzle` връща страницата, а не `404`. Потвърдено е и предположението, че `PORT=8080` е достатъчен и че безплатната база приема връзки отвън, за да се пуснат `migrate` и `seed` от компютъра.

**Какво означава това**

- Има истинско демо, което може да се показва и тества в мрежата, с фалшиви данни и без плащания. Каталогът (категории, списък, страница на продукт) е изцяло работещ от край до край.
- Новият код от `main` се внедрява сам, когато проверките в GitHub са зелени. Нова миграция обаче не се прилага сама: след нея `migrate` се пуска ръчно (решение [0012](docs/decisions/0012-demo-migrations-and-seed-run-by-hand.md)), иначе API и схемата се разминават.
- Демото е на безплатния план, затова не е стабилно: услугите заспиват след 15 минути (първата заявка е бавна), а **базата изтича на 2026-12-08**. Тогава демото трябва да се създаде наново (нова база, `migrate`, `seed`) или да се мине на платен план. Това не е сигурен дом на данни и не е продукция.
- Снимките в галерията са вградената снимка по подразбиране, защото няма хранилище и файлове (виж „Чака: демо снимки“ в `docs/project-start.md`). Поръчки и тестово плащане има в кода (задачи 18–26), но не са пуснати в демото в render.com, докато не се приложат миграциите там. Кодът има админ вход и панел за категории, продукти, снимки и настройки (задачи 10–14), но демото в render.com ги показва само ако са приложени миграциите и е създаден администратор, а те са ръчни стъпки (решение [0012](docs/decisions/0012-demo-migrations-and-seed-run-by-hand.md)).

**Какво още не е направено от задача 9:** не е измерено колко време отнема първата заявка след заспиване (ръчно, по-горе); не е проверено в браузър за грешки в конзолата за CORS и CSP.

## Договор на API (`openapi.json`)

Договорът е в `src/web/shared/openapi.json`, а типовете на фронтенда се генерират от него. След промяна на API: пусни API в среда `Development`, свали `/openapi/v1.json` в този файл и пусни `npm run api:types --workspace @storefront/shared` от `src/web`. Подробности са в [new-feature.md](docs/handbook/new-feature.md), стъпка 6.
